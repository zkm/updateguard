Pre-reboot verification for Linux updates

Know it will boot before you reboot.

updateguard snapshots your system before risky kernel, driver and bootloader updates, then checks that the machine will actually come back up. When something's wrong it says don't reboot and prints the command that fixes it.

How it works

It hooks into your package manager on both sides of the update.

It only wakes up for packages that can break booting: kernels, DKMS and NVIDIA drivers, initramfs tools, bootloaders, systemd, glibc, microcode and storage tools. A browser update passes through silently.

Before

Snapshot and pre-flight

  • Stops the update if /boot is in fstab but not mounted
  • Snapshots / with snapper, snap-pac or raw btrfs
  • Copies kernel and initramfs off a separate boot partition
During

Your update runs

pacman or apt installs packages and runs its own hooks: mkinitcpio or update-initramfs, DKMS builds, bootloader updates.

After

Boot-health check

  • Runs after every other hook has finished
  • Verifies kernel, initramfs, DKMS, boot entries and free space
  • On failure: don't reboot, here's the fix, here's the rollback

What it checks

The failures that turn a routine update into a live USB.

CheckCatches
The kernel on /boot byte-matches the installed one (or dpkg's md5sum)A stale kernel on /boot because the partition wasn't mounted during the update
Each initramfs exists, is newer than the kernel package and contains lib/modules/<kver>An initramfs that wasn't regenerated, or was built for the wrong kernel
Each UKI's embedded .linux section matches the installed kernelA unified kernel image that wasn't rebuilt
Headers are present and every DKMS module is installed for every kernelNVIDIA, ZFS or v4l2loopback not built, so a black screen on reboot
systemd-boot, GRUB and Limine entries point at files that existBroken or stale boot entries
Boot partition free spaceA full ESP truncating initramfs writes
The running kernel's modules are still on diskThe "reboot soon" case before new modules can load

Distributions

Built on Arch, headed for your servers.

Arch updates the kernel and DKMS constantly, which makes it the proving ground. Debian, Ubuntu and the RHEL family are in preview on the way to your servers.

Available

Arch & CachyOS

pacman hooks, mkinitcpio images and UKIs, systemd-boot, GRUB and Limine. Snapshots with snapper, snap-pac or raw btrfs.

Preview

Debian & Ubuntu

apt hooks, dpkg-verified kernels, initramfs-tools and GRUB. Most servers run ext4, so it verifies even where it can't snapshot.

Preview

Rocky, Alma & Fedora

dnf 4 plugin and dnf5 actions, rpm-verified kernels, dracut images, kernel-install layouts (GRUB, systemd-boot, UKIs), BLS entries and akmods. Snapper on Fedora's btrfs.

Install

Starts in dry run. It reports and never blocks until you say so.

Watch a kernel update or two, confirm the output matches what you know about the machine, then set DRY_RUN=0 in /etc/updateguard.conf.

Arch & CachyOS

git clone https://github.com/zkm/updateguard.git
cd updateguard
makepkg -si
sudo updateguard doctor

Debian, Ubuntu, Rocky, Alma & Fedora (preview)

git clone https://github.com/zkm/updateguard.git
cd updateguard
sudo ./install.sh --apply
sudo updateguard doctor

install.sh picks apt or dnf hooks. Fedora 41+ (dnf5) needs sudo dnf install libdnf5-plugin-actions first.

Roadmap

What comes next.

  1. Debian & Ubuntu on real machines. Testing on 22.04, 24.04 and Debian 12, a .deb package, and rollback for ext4 servers with LVM snapshots.
  2. RHEL family on real machines. Real transactions on Rocky and Alma 9 and Fedora 41+, an .rpm package, and LVM snapshots for XFS servers.
  3. Fleet reporting. updateguard check --json from every machine to one dashboard, with an alert when a server shouldn't be rebooted.
  4. Automatic rollback. Once the checks have proven themselves on real updates.
